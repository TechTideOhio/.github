# Contributing to TechTide AI Projects

Thank you for considering a contribution. TechTide AI welcomes focused improvements to documentation, tests, tooling, and implementation. This guide provides the organization-wide baseline; a repository’s own `CONTRIBUTING.md`, development documentation, license, and security policy take precedence when they exist.

## Before You Begin

Please search existing issues and pull requests before starting work. For substantial proposals, open an issue or discussion in the affected repository before implementation so that scope, approach, and maintenance expectations can be aligned early. All participants must follow the [Code of Conduct](CODE_OF_CONDUCT.md).

> Do not report security vulnerabilities in public issues. Follow the private reporting path in [SECURITY.md](SECURITY.md).

## Contribution Workflow

| Stage | Expectation |
|---|---|
| **Scope** | Describe the user problem, proposed outcome, and repository affected. Link the relevant issue when one exists. |
| **Prepare** | Fork the project or create a branch from the default branch. Follow the repository’s documented setup and tooling. |
| **Implement** | Keep the change focused. Include tests or documentation updates whenever the project requires them. Avoid unrelated formatting or refactoring. |
| **Validate** | Run the project’s relevant checks locally and explain any checks that could not be run. |
| **Submit** | Use the pull-request template, summarize the change and validation, and respond constructively to review feedback. |

## Pull Request Standards

A high-quality pull request is small enough to review, explains its intent, and leaves the repository easier to maintain. Use a descriptive title, document externally visible behavior changes, and include test evidence appropriate to the repository. Do not commit credentials, personal data, generated binaries, or unrelated lockfile churn.

When a change affects behavior, configuration, interfaces, security boundaries, or release notes, call this out explicitly. Maintainers may ask for a focused follow-up pull request when a submission combines independent changes.

## Documentation Contributions

Documentation should be accurate, task-oriented, and kept close to the code or policy it describes. Use clear headings, meaningful link text, and examples that can be maintained. The organization-profile repository validates Markdown and external links automatically; please resolve validation failures before requesting review.

## Licensing

By submitting a contribution, you agree that it may be distributed under the license of the repository to which you contribute. Review that repository’s license before submitting substantial work. The organization-profile repository itself contains policy and profile material; it does not establish a license for other repositories.

## Getting Help

For product help, a general question, or a non-security contact request, use the routes in [SUPPORT.md](SUPPORT.md).
